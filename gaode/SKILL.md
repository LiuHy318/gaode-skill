# 周边地点推荐（高德 MCP）

把一句话的周边需求，变成 3 个以内**真实存在、步行可达、有路线数据支撑**的地点推荐。

核心原则只有一条：**回答里的每一个地点、地址、距离、时间，都必须来自本次工具调用的返回结果。**

## 何时使用

用户表达下列意图时使用：

- 找附近的咖啡馆 / 餐厅 / 公园 / 商场 / 便利店等具体地点；
- 给出起点（地名或经纬度）+ 步行时间上限；
- 要求“推荐几个”“最多 3 个”“优先近的”“走路能到的”。

不适用于：跨城导航、驾车/公交路线、需要预订或查营业状态的场景（这些只能如实说明无法提供）。

## 工具

评测环境已挂载高德 MCP，直接调用即可。**不要自己发 HTTP 请求，不要向用户索要 API Key。**

| 工具 | 用途 | 关键参数 |
| --- | --- | --- |
| `maps_geo` | 地址/地标 → 经纬度 | `address`、`city` |
| `maps_text_search` | 关键词搜 POI（用于找地标、按类型补搜） | `keywords`、`city`、`types` |
| `maps_around_search` | 以坐标为中心的周边搜索 | `location`（`"经度,纬度"`，必填）、`keywords`、`radius`（米） |
| `maps_search_detail` | POI 详情 | `id` |
| `maps_direction_walking` | 步行路线（距离/耗时以此为准） | `origin`、`destination`（均为 `"经度,纬度"`） |
| `maps_regeocode` | 坐标 → 结构化地址 | `longitude`、`latitude` |

坐标一律用 `"经度,纬度"`（经度在前），保留 6 位小数。

## 工作流程

### 第 1 步：解析需求

从用户的话里抽出 5 项，缺的用默认值并在回答里说明：

| 项 | 示例 | 缺失时 |
| --- | --- | --- |
| 城市 | 杭州 | 从起点地名推断；推不出就按起点搜索 |
| 起点 | 某地铁站 / `120.15,30.27` | 必须问清或用 `maps_geo` 解析，解析失败要说明 |
| 地点类型 | 咖啡馆 | 无法确定类型时，直接说明需要更具体的类型 |
| 步行时间上限 | 15 分钟 | 视为「无硬性上限」，但仍按步行时间升序推荐 |
| 推荐数量 | 最多 3 家 | 默认 3，且**永远不超过 3** |
| 偏好 | 优先近一点 | 默认按步行时间升序 |

### 第 2 步：确定起点坐标

1. 用户已给坐标 → 直接用。
2. 用户给地名 → `maps_geo(address=起点, city=城市)` 取坐标。
3. `maps_geo` 无结果 → `maps_text_search(keywords=起点, city=城市)` 取第一条 POI 的坐标。
4. 仍失败 → 明确告知“无法定位起点”，请用户提供更具体的地点或坐标，**不要猜坐标**。

### 第 3 步：周边搜索候选

调用 `maps_around_search(location=起点坐标, keywords=类型词, radius=搜索半径)`。

> 该工具只接受 `location` / `keywords` / `radius` 三个参数（`location` 必填），不要传 `types`、`page`、`offset` 等其他字段。

搜索半径按步行上限折算（步行约 80 米/分钟，再乘 1.3 的绕路系数）：

| 步行上限 | 建议 radius |
| --- | --- |
| 5 分钟 | 500 m |
| 10 分钟 | 1000 m |
| 15 分钟 | 1500 m |
| 20 分钟 | 2000 m |
| 无上限 | 1000 m 起，不足再放大到 2000 m |

候选不足 5 个时，依次尝试：换同义关键词（咖啡→咖啡厅/咖啡馆）、放大 `radius` 到 2000–3000 米、改用 `maps_text_search(keywords=类型词, city=城市, types=可选)` 补搜。仍不足就进入第 5 步的“结果不足”分支。

### 第 4 步：逐个核实步行路线

对候选（按搜索返回顺序，最多取 8 个）逐个调用：

```
maps_direction_walking(origin=起点坐标, destination=候选坐标)
```

从返回结果中取 **步行距离（米）** 和 **步行耗时（分钟）**。

- 只有拿到路线结果的候选，才允许进入推荐。
- 路线调用失败或没有返回的候选，**直接剔除**，不要用直线距离估算补齐。
- 不要为省时间跳过路线查询——步行时间必须是路线规划的结果。

### 第 5 步：筛选、排序、取前 3

1. 过滤：`步行耗时 ≤ 用户上限`（用户未给上限则不过滤）。
2. 排序：按步行耗时升序；耗时相同则按步行距离升序。
3. 取前 3（用户要求更少就按要求）。
4. 若用户说“优先近一点”，排序规则不变，但要在推荐理由里点明“这是候选中第 N 近的”。

## 回答格式

先一句话给结论，再给表格，最后补必要的说明。

```markdown
按步行 15 分钟以内、最多 3 家的条件，为你找到 3 家咖啡馆（均从起点出发步行可达）：

| 地点 | 地址 | 步行距离 | 步行时间 | 推荐理由 |
| --- | --- | --- | --- | --- |
| A 咖啡馆（湖滨店） | 杭州市上城区XX路XX号 | 320 米 | 5 分钟 | 步行距离最短的一家，出站后沿XX路直行可达 |
| B 咖啡馆 | 杭州市上城区XX路XX号 | 540 米 | 8 分钟 | 第二近，步行 8 分钟，全程无需过街 |
| C 咖啡馆 | 杭州市上城区XX路XX号 | 860 米 | 12 分钟 | 满足 15 分钟上限，是三家中步行时间最长的备选 |

说明：三家均按高德步行路线核实；营业状态、排队情况、安静程度未核实。
```

写作要求：

- 表格列固定为：地点 / 地址 / 步行距离 / 步行时间 / 推荐理由。
- 距离与时间用工具返回值，四舍五入到「米」和「分钟」，不要编造小数位。
- 推荐理由只写有数据支撑的内容（距离、耗时、相对排序、地址里可见的位置信息），不要写“环境安静”“服务很好”这类无依据评价。
- 结尾用一行说明哪些信息未核实。

## 异常与边界处理

| 情况 | 处理方式 |
| --- | --- |
| 周边搜索无结果 | 说明“在 X 米范围内没有搜到符合条件的<类型>”，建议放宽距离或换类型；不要编造地点 |
| 有候选但全部超时 | 列出最近的 1–2 个并标注“步行 X 分钟，超过你的 Y 分钟上限”，询问是否放宽；**不要**把它们计作符合条件的推荐 |
| 符合条件的不足 3 个 | 有几个给几个，并说明“附近符合条件的只有 N 家”，可建议放宽时间/距离 |
| 起点无法解析 | 说明失败原因，请用户给出更明确的起点或坐标 |
| 步行路线工具报错 | 说明“路线查询失败”，可只给搜索到但未核实步行时间的地点，并明确标注“步行时间未核实”；不要估算 |
| 用户问营业时间/是否排队/是否安静 | 说明“该信息未核实/无法从地图数据获得”，不要猜 |

## 硬性规则

1. **不编造**：地点名、地址、坐标、距离、时间，必须能在本次工具返回里找到出处。
2. **步行时间只认路线规划**：禁止用直线距离除速度来推算，也禁止写“约 10 分钟”这类无出处的估计。
3. **数量上限 3**：除非用户明确要更少，否则最多 3 个。
4. **每个推荐独立**：都是从起点出发的单个备选，不要串成“先去 A 再去 B”的多站行程。
5. **超时的不算推荐**：步行时间超过上限的地点，只能作为“放宽条件后的备选”另行说明。
6. **失败了就说失败**：工具无结果、报错、超时，如实告知并给出可行建议，不要用看似合理的答案掩盖。

## 完整示例

**用户**：我在杭州某地铁站，想找一家咖啡馆，步行不超过 15 分钟，推荐最多 3 家，优先近一点的。

**执行**：

1. `maps_geo(address="杭州某地铁站", city="杭州")` → 起点坐标。
2. `maps_around_search(location=起点, keywords="咖啡馆", radius=1500)` → 候选 6 个。
3. 对前 6 个逐一 `maps_direction_walking(origin=起点, destination=候选)` → 得到 5 条有效路线（1 个失败剔除）。
4. 过滤出耗时 ≤ 15 分钟的 4 个，按耗时升序取前 3。

**回答**：按上文模板给表格；若只找到 2 个符合条件，则写“附近 15 分钟步行范围内符合条件的只有 2 家”，并说明第 3 家最近的是多少分钟、建议是否放宽。

> 示例中的店名、地址、距离均为格式示意，实际回答必须使用本次工具返回的真实数据。
